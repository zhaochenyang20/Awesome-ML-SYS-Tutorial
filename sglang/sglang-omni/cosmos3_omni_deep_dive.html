一份权重，两种解码

MoT 的模态解耦、AR + diffusion 的联合注意力、以及它对 Omni serving 抽象的含义

Cosmos 3 用 Mixture-of-Transformers 把两种运行时特征完全不同的解码方式——文本的自回归 decode 与其余模态的 diffusion 去噪——装进同一份权重、同一条序列、同一次注意力里。本材料从底层机制一路拆到 serving 抽象：先讲清"混合"到底混的是什么，再给出三种 attention 的数学、完整的 decode 过程与伪代码、latent 的本质，最后落到我们 SGLang Omni 的抽象取向上。

01 — 架构总览

MoT 双塔：5 套按模态分开的权重，共用一次注意力

Cosmos 3 是 Mixture-of-Transformers。它不是一个"通用大脑"，而是把每个模态的权重分开、再用一次共享注意力缝在一起。文本走自回归塔，image / video / audio / action 走 diffusion 塔。

02 — 概念澄清

"混合"到底混的是什么

最常见的误解：以为有一个参数一会儿去噪、一会儿 decode。没有这种参数。 MoT 的"mixture"指的是一个 transformer 里同时装着好几套按模态分开的权重，一条混合序列流过去，每个 token 按模态被路由到自己那套。

MoT 论文把这件事说得很干净：它按模态解耦所有非 embedding 参数——feed-forward、attention 投影矩阵、layer normalization——每个模态各一套，唯独 self-attention 作为一次操作对全序列共享。所以 text 权重永远只处理 text token，image 权重永远只处理图像 latent，从不换岗。

为什么"不共享参数"和"同一次 attention"不矛盾

关键点一句话：attention 这个"混合"操作本身没有可学习参数。 参数全在两侧的投影（Q/K/V/O）和 FFN 里，而这些都是各模态一套。中间那次把它们缝起来的 softmax(QK⊤)V 是零参数的——它只是把各自算好的 q/k/v 混在一起。拆开一层看：

稀疏激活：不是每次 forward 都用全部参数

因为参数按模态解耦，一次 forward 真正激活的只是"这次序列里出现的那几个模态的那几套权重"，其余模态的 FFN / 投影一个都不碰。这是 MoT 被称为"稀疏"的原因（论文里 speech 只用 dense 基线约 37% 的 FLOPs、Chameleon 设定约 56%）。要区分两件事：

维度是否稀疏含义
每次 forward 的 active 参数（FLOPs）稀疏只算出现模态那几套，"全用到"是错的
需要驻留显存的参数（loading）不一定通用 any-to-any 服务事先不知下个请求带什么模态，往往仍需全部驻留；省显存靠单一用途部署只 load 需要那片（这正是单独的 Cosmos3ReasonerForConditionalGeneration arch class 存在的意义）
03 — 对照

和 Ming-Omni 的区别：联合注意力 vs 交棒

直觉上 Cosmos 和 Ming-Omni 很像——都是"一个 AR 部分 + 一个 diffusion 部分，参数分开"。这个层面对。差别在耦合的紧度。

Ming-OmniCosmos MoT
结构dedicated encoders → Ling(MoE)理解+出文本 → 交棒给独立的 audio decoder / diffusion 模型只有一叠层；text token 与 latent 从头到尾在同一条序列
注意力两套：backbone 一套、diffusion 一套，各自独立每层一次共享注意力，跨模态互相看
条件如何进入生成backbone 产出 conditioning，一次性喂给下游网络latent 在每一层的同一次 attention 里读条件（深、双向、逐层）
能否干净切成两 stage能（thinker → diffusion，relay 传 hidden state）难——没有"交棒点"，整个生成是一次融合 forward

比喻只用一次：Ming 是两场会，A 会写纪要、B 会开场念一遍；MoT 是所有人坐同一张桌子，每一层实时对话——各说各的语言（各自权重），但同一场对话（同一次 attention）。这个差别对我们划 Stage 有直接后果，见 第 10 节。

04 — 数学

三种 attention 的数学

三者的差别几乎全在掩码和用几套投影上，核心公式是同一个 softmax。记号：位置 p 的隐状态 hp，投影出 q/k/v，头维 d。

① 传统自回归（因果掩码）

一套权重，所有 token 共用：

qi = WQ hi ， ki = WK hi ， vi = WV hi
αij = softmaxj( qi · kj / √d ) ， 仅 j ≤ i（因果 / 下三角）
oi = Σj≤i αij vj

每个 token 只看自己和过去。生成逐 token 串行，过去的 k/v 进 KV-cache。目标：next-token 交叉熵。

② 传统 diffusion（DiT，全连接）

latent token z1..m = 整张（带噪）图/视频在噪声档 t 的表示，t 经 AdaLN 或 embedding 注入。一套权重：

qi = WQ zi ， …（zi 依噪声档 t）
αij = softmaxj( qi · kj / √d ) ， 所有 j（全连接 / 双向）
oi = Σj αij vj ，网络预测 εθ(zt, t, c)，跑 T 步

每个 patch 看到所有 patch，无因果结构。一次 forward = 一个去噪步；步与步之间 z 全变，没有 KV-cache。

③ Cosmos（MoT + Transfusion 式联合）

一条序列混着 text token 和 latent，位置 p 的模态 m(p)。投影按模态分开；掩码是块因果混合：

qp = WQm(p) hp ， kp = WKm(p) hp ， vp = WVm(p) hp
αpq = softmaxq( qp · kq / √d + Mpq ) ， op = Σq αpq vq
Mpq = 0（可见）/ −∞（不可见）
text p：因果（q 在更早块，或 q ≤ p）　　image p∈块B：{B 之前的全部} ∪ {B 内全部，双向}

关键：不管哪套 W，qp 和 kq 都落在同一个 ℝd，所以跨模态的 qp·kq 是有定义的实数——这就是文本和图像"能对话"的数学入口。三种掩码画成矩阵：

index 级走一遍

最小序列 [t1, t2, i1, i2, i3]，位置 1、2 是文本，3、4、5 是一个图像块。取图像 query i2（pos 4），它可见 {1,2,3,4,5}：

s4,1 = q4·k1 / √d （q4=WQimgh4，k1=WKtxth1） ← 图 query · 文本 key
s4,2 = q4·k2 / √d ← 图 query · 文本 key
s4,3, s4,4, s4,5 ← 图 · 图（块内双向，含"后面的" i3）
α4,· = softmax( {s4,1 … s4,5} )
o4 = α4,1v1 + α4,2v2 + α4,3v3 + α4,4v4 + α4,5v5

o4 是一个横跨文本 value（紫，WVtxt）和图像 value（青，WVimg）的凸组合。文本条件就在这一个加权和里进到图像 patch——没有第二个网络、没有交棒，只是同一个 softmax 的分母里既有文本 key 又有图像 key。掩码决定这行在哪些 q 上求和，模态决定每个位置的 q/k/v 由哪套 W 算，两者塞进同一个 softmax(QK⊤/√d + M)V。

05 — KV-cache

为什么 diffusion 的 latent 不能 KV-cache

KV-cache 是"增量式序列扩展"的优化，成立要同时满足两条：上下文 append-only（只在末尾追加），且已有位置的隐状态被冻住（k/v 固定可复用）。diffusion 的循环两条全破。

前提AR decodediffusion 去噪
是不是 append-only是，逐 token 在末尾追加否，token 数始终 m，没有"新位置"
已有位置隐状态是否冻结是，x1..t 永不再变 → k/v 固定否，去噪定义就是 z(s−1) ≠ z(s)，每步 h 全变 → k/v 每步不同
z(T) → z(T−1) → … → z(0) （定长 m 个 latent，反复精修，不扩展）
kj(s−1) = WK hj(s−1) ≠ WK hj(s) = kj(s) ← 上一步缓存的 k/v 这一步是错的，必须全重算
两个边界（别记死）：①固定的条件（文本 prompt）在 T 步里不变，其 k/v 算一次可复用 T 步——不能缓存的严格来说只是正在被去噪的那些 latent。②DeepCache 一类跨相邻步复用特征是近似（相邻步特征变化慢），不是精确 KV 复用，别混。
06 — 解码全过程

完整 decode 过程

底层只有两个解码 primitive，任何模态组合的请求都是这两个按控制 token 编排出的序列。

primitive · AR 步

尾部 append 1 个离散 token，因果注意力，k/v 立即入 cache 并永久复用。文本走这个，逐 token 增长。

primitive · 去噪块

尾部 append 固定 m 个连续 latent，块内双向 + attend 前缀，原地迭代去噪 T 步，完事整块 k/v 入 cache。image / video / audio / action 走这个，块长不变。

相位模型：严格 append-only，一次只有一个区域活动

整条序列从左往右一块一块长出来。任何时刻只有一个区域"活动"，它左边全部冻结、右边尚不存在。text 段和 latent 块不会同时活动——这就是"text 从中间变长、latent 同时在动"这种矛盾场景根本不存在的原因。

主循环

prefix_kv = [ {"K": empty[0,d], "V": empty[0,d]} for _ in range(L) ]  # 逐层各一份
H = 0; h_new = embed(BOS)
while not done:
    # ===== AR 文本相位 =====
    while True:
        x = decode_one_text_token(h_new, pos=H, prefix_kv); H += 1
        if x == <EOS>: done = True; break
        if x == <BOI>: break        # begin-image/audio/video/action
        h_new = embed(x)
    if done: break

    # ===== 去噪相位（块大小 m 此刻定死）=====
    m = resolve_block_size(spec)              # 图=patch数; 视频=帧×patch; 音频=帧率×时长; action=步数×D
    block_positions = range(H, H+m)           # 位置 id 立刻确定，去噪中不变
    z = noise(m)                              # z^(T)
    for s in range(T, 0, -1):
        eps = forward_denoise(z, s, block_positions, prefix_kv)  # 只前向这 m 个
        z   = sampler_update(z, eps, s)                          # z^(s)→z^(s-1)，在网络之外改 z
    finalize_block_into_cache(z, block_positions, prefix_kv); H += m  # clean K/V 入 cache
    h_new = embed(<EOI>)

两个内层：AR 单步 与 去噪单步（差别全在这里）

# —— AR：只新增 1 个位置，拼前缀 KV，算完 append（append-only）——
def decode_one_text_token(h_new, pos, prefix_kv):
    for l in range(L):
        h = layernorm_txt[l](h_new)
        q,k,v = W_Q_txt[l]@h, W_K_txt[l]@h, W_V_txt[l]@h      # 文本投影
        q,k = rope(q,pos), rope(k,pos)
        K = concat(prefix_kv[l]["K"], k); V = concat(prefix_kv[l]["V"], v)   # [H+1, d]
        a = softmax(q@K.T / sqrt(d)); o = a@V                 # 因果：新 token 看全部 H+1，无需显式 mask
        h_new = h_new + W_O_txt[l]@o; h_new = h_new + FFN_txt[l](h_new)
        prefix_kv[l]["K"], prefix_kv[l]["V"] = K, V           # append，永不再改
    return sample(unembed(h_new))

# —— 去噪：只前向这 m 个 latent，读前缀 KV 但不写；块内双向 ——
def forward_denoise(z, s, block_positions, prefix_kv):
    h = latent_in_proj(z) + timestep_embed(s)                 # [m, D]，噪声档注入
    for l in range(L):
        hn = layernorm_img[l](h)
        q,k,v = hn@W_Q_img[l].T, hn@W_K_img[l].T, hn@W_V_img[l].T   # [m,d] 每步重算(z 变了)
        q,k = rope(q,block_positions), rope(k,block_positions)      # 位置=常量
        Kp,Vp = prefix_kv[l]["K"], prefix_kv[l]["V"]          # [H,d] 冻结，读缓存不重算
        K = concat(Kp,k); V = concat(Vp,v)                    # [H+m, d]
        a = softmax(q@K.T / sqrt(d))                          # [m, H+m]，块内无下三角=双向
        h = h + (a@V)@W_O_img[l].T; h = h + FFN_img[l](h)
        # 注意：这里绝不写 prefix_kv[l]，去噪中途不落 cache
    return eps_head(h)                                        # [m, D_latent] 预测噪声/velocity

第三个内层：块 finalize（去噪完 → clean K/V 入 cache）

# —— 去噪跑完 z 是 z^(0)(clean)，用 clean 的 K/V 整块 append，此后这块变成冻结前缀 ——
def finalize_block_into_cache(z0, block_positions, prefix_kv):
    h0 = latent_in_proj(z0)                               # clean latent，不再加噪声档 embedding
    for l in range(L):
        hn = layernorm_img[l](h0)
        k  = rope(hn@W_K_img[l].T, block_positions)        # 位置=同一批常量
        v  =      hn@W_V_img[l].T
        prefix_kv[l]["K"] = concat(prefix_kv[l]["K"], k)   # H → H+m
        prefix_kv[l]["V"] = concat(prefix_kv[l]["V"], v)   # 此后冻结、可被后续 text 复用

注意入 cache 用的是 clean 的 z(0)，不是去噪中途某步：后续文本 token attend 的语义必须是"已经画好的图"。至此三件套齐全——主循环编排 decode_one_text_token（AR 步）、forward_denoise（去噪块单步）、finalize_block_into_cache（落 cache），任何模态请求都是这三者的排列组合。

latent 每步在变的唯一来源是采样器，不是 text：sampler_update 是网络之外的闭式更新（DDIM/flow-matching），把当前带噪 z 和预测 eps 推进一格 z(s−1)。z 变了 → 下一次 forward_denoise 里 h、q/k/v 都变 → 所以不能跨步复用它们的 KV；而前缀没进过这个更新，纹丝不动，所以能复用。

逐区域的 KV 行为

区域长度生成它时自身 K/V同时前缀 K/Vfinalize 后
text span逐 token 增长算一次即缓存、复用复用冻结入 cache
latent block固定 m每去噪步全重算复用（前缀是冻的）用 clean z 的 K/V 整块入 cache

所以同一次生成里 KV 是"前缀缓存、去噪块每步重算"的第三种形态——既非纯 AR 的全缓存，也非纯 DiT 的全不缓存。这是 scheduler 要单列处理的一类。（细节：入 cache 用的是 z(0) clean 的 K/V，因为后续文本 attend 的是"已经画好的图"。）

07 — 路径

Reasoner vs Generator

上面那套"AR + 去噪交替"的混合解码是 Generator 独有的；Reasoner 是它的退化情形——序列里一个去噪块都没有，只剩纯 AR。判据是输出模态，不是输入。

ReasonerGenerator
触发输出 = 纯 text输出含 image/video/audio/action
序列里有无去噪块无有（一个或多个）
相位全程 AR 一个相位AR 文本相位 ↔ 去噪相位 交替
用到的权重text 权重 + 输入侧编码上述 + 目标模态 diffusion 权重
KV 行为全程逐 token 增量缓存text 段增量缓存；去噪块每步重算自身、复用前缀、完事整块入缓存
能否单独部署可（arch class 只 load 理解侧）需 diffusion 那套权重

输入模态只决定前缀里放什么 condition token，输出模态决定走哪条路径、有没有去噪相位。 这也是那个 CI 盲点的根：同样的输入组合（比如 image+text），输出不同（text vs video）→ code path 完全不重叠。覆盖矩阵的第一维必须是 (input set, output modality) pair。

08 — 实例

各模态请求实例

记号：[...] 是一段 token 及其权重/角色；⟨denoise m⟩ 表示尾部追加 m 个 latent 并原地去噪 T 步、完事入 cache。

text → audio + text（如"念这句并给文字稿"）：前缀塞 text 条件 → AR 出文字稿到 <BOA> → ⟨denoise ma 个 audio latent，attend 前缀 text 含刚写的文字稿，这就是"念的和写的一致"的来源⟩ → 可续文本 → <EOS>。

img+text → action：前缀 image 编码 + text 指令 → 直接 ⟨denoise mact 个 action latent；mact = 步数 × embodiment 维度 D（单臂 Franka 10D、Agibot 29D…）⟩。无 AR 文本段。

image → video (i2v)：前缀首帧编码 → ⟨denoise mv 个 video latent，时空双向 + attend 首帧⟩。forward-dynamics rollout 是它的分块自回归版：[首帧][action_chunk_0]⟨denoise chunk0⟩ → 取生成视频最后一帧当下一块首帧 → 再来一块。

09 — latent

latent 的本质，与如何和 text 一起 attention

latent 不是"各模态的统一 embedding"。恰恰相反：各模态的 latent 是各自独立、彼此不通用的向量。它们能和 text 同场 attention，靠的不是统一表示，而是被各自的投影映射到同一个 d 维打分空间。

latent 是各模态本地的连续张量

latent 是该模态自己的编码器压出来的：image latent = VAE 把图压成 [h×w, c] 的 patch 网格；video latent = 时空 VAE 的 [帧′×h′×w′, c]；audio latent = 音频 VAE 的 [帧, c]；action latent = 轨迹的 [T, D]。它们之间没有共享语义，维度 c 都可能不同。Cosmos 恰恰没有把所有模态塞进一个通用表示。

统一的是投影之后的 d 维空间，不是 latent

text 那边也一样本地（查表得 [D_text]）。让它们"能对话"的是每个模态各自的输入投影 + Q/K/V 投影，把本地表示拉到同一个头维 d：

text:　e = embed_table[tok] [D_txt] → h = in_proj_txt(e) [D] → q = WQtxt·LN(h) [d]
image: z = vae_encode(patch) [c_img] → h = in_proj_img(z) [D] → q = WQimg·LN(h) [d]
起点不同、维度不同，但两条 in_proj 各自拉到同一主干宽度 D，再各自的 W 拉到同一 d
→ qimg · ktxt / √d 是两个同维实向量的点积 = 一个普通标量。attention 只对 d 维向量做点积，不关心来源。

类比只一句：不同货币各按自己汇率换成美元后就能加总——latent 是各国货币（不通用），in_proj + WQ/K/V 是各自汇率，d 维空间是美元，attention 只在"美元"层做算术。这也正是"MoT 参数按模态分开"的落点：每个模态需要自己的一条接入路径。

latent → 模态 decoder：还原到信号域

去噪产出的是目标模态的 latent，不是可播波形 / 可看像素。后面还挂一个模态专属 decoder 把 latent 拉回信号域：audio latent → vocoder/codec → waveform；video/image latent → VAE decoder → 逐帧像素。这跟 latent diffusion 一个套路（低维 latent 去噪，末端 VAE/vocoder 拉回高维）。

两个措辞要拧准：① Cosmos diffusion 路径去噪的是连续 latent，不是离散 "audio token"（后者是 Qwen3 talker / Fish 那种 AR codebook 路线，机制不同）。② 这个 decoder 通常是主体之外独立训练的 VAE/vocoder，不在那 L 层 MoT 里、不参与联合 attention——所以它天然是流水线上另一个（可流式的）terminal stage，中间走 relay 传 latent。
10 — 抽象

对 SGLang Omni 的抽象含义

真实分层是 Coordinator → Stage → Scheduler → ModelRunner → forward；relay（含 CommEngine）是 Stage 之下、沿图的边搬 tensor 的正交传输，不在 ModelRunner 之上。统一发生在 Stage 这个 model-agnostic 的 IO 壳（"从不检查 scheduler 类型"），异构性下推到 Scheduler / ModelRunner。

判断一

统一在 Stage 壳，不在通讯层

KV-cache / continuous batching 对 diffusion 无意义，CFG / denoising scheduler 对 AR 无意义。硬统一 Engine = 造一个 if-modality 分支体。正确缝合点是 Stage（一条 code path，从不检查 scheduler 类型），异构性下推到 Scheduler / ModelRunner。Cosmos 的 Reasoner / Generator 落在不相交的权重子集上，正是它们该是不同 runner、能各自 disaggregate 只 load 自己那片的根据。

判断二

去噪块是同一个 primitive 的不同实例化

image/video/audio/action 的解码机制相同（块内双向 + 去噪 T 步），不同的只是三个参数化：走哪套 diffusion 权重、块大小 m 怎么算、块内位置编码（2D/3D/1D）。所以不需要每模态一套 decode loop——一套"去噪块" DiffusionModelRunner + 按模态注入（权重、m、位置编码）即可。这正对上文档里 DiffusionModelRunner 想成为一等 runner 的设计。

判断三

KV 的"第三种形态"要 scheduler 单列

一次生成请求里 KV 是"前缀缓存、去噪块每步重算、完事整块入缓存"的混合。既不是纯 AR 的全缓存，也不是纯 DiT 的全不缓存。内存回收、抢占、显存预算都要按这个形态设计——而不是套用 LLM 的 KV 管理。

判断四

联合注意力抗拒 thinker→talker 式的两段切分

Ming 松耦合，天然两 Stage（thinker → diffusion，relay 传 hidden state）。Cosmos 若是真 joint-attention，去噪块每一层都要在同一次 attention 里读文本条件，没有交棒点——整个生成是一次融合 forward，更想当成一个 Stage 里跑一个既做 AR 条件又做去噪的 runner。这可能是它对我们现有 producer-consumer 切法最大的挑战。（而末端的 VAE/vocoder 还原级仍是可干净切出的另一个 stage。）

11 — 诚实边界

诚实边界：什么是读法、什么要 white paper 才能敲死

本材料第 02、04、06 节的"单序列内 AR 段与去噪块交替 + block-causal 掩码 + 模态解耦投影"是 MoT + Transfusion 的读法。卡片说了 MoT / single framework / AR 塔 / diffusion 塔，这些指向这个读法（MoT 论文本身就研究了文本 AR + 图像 diffusion 同处一个 transformer 的设定）。但卡片没有逐字确认以下几点，需要 white paper / config / HF arch class 实现才能坐实：

存疑点若为 A（联合，本材料读法）若为 B（cross-attention 交棒，更像 Ming）
文本 K/V 与 latent 的关系同一个 softmax 的分母里（联合）单独一次 cross-attention（交棒）
能否两段切分难，整生成一次融合 forward可，backbone → diffusion 两 stage
两塔是否共享 attention 序列是否，各自独立栈

另需实现确认的：两塔间是否有共享 trunk、输入 encoder 塔是否独立于 MoT backbone、Reasoner arch class 实际砍掉了多少、以及 Cosmos SGLang cookbook 里 diffusion 挂在哪个 scheduler 下。这些不影响本材料对机制原理的描述，但会影响落到我们 Stage / runner 上的具体切法。
